Release audit for v0.43.1 (round 1, gate 3) flagged
tests/test_post_tool_total_processes_1011.py:147-158 (`_materialize_tree`, added in
9773848 #1028).

What was observed: if `v0.42.4` or `v0.43.0` does not resolve in the checkout, the
test runs `git -C REPO_ROOT fetch --depth=1 origin tag <tag>` against the developer's
own working repository rather than a throwaway clone. In a complete (non-shallow)
clone that writes `.git/shallow`, turning a full clone into a shallow one for the
rest of that session. History below the tagged commit then disappears from
`git log`, and `release_delta.py` reports `could-not-run` for shallow clones.

Who hits it: someone running `pytest` locally on Linux with `strace` on PATH (the
test is skipped otherwise), in a clone made with `--no-tags` or otherwise missing
those two tags, with `origin` able to serve them. CI's own checkout is already
shallow, so CI is not affected.

How it was confirmed (per the auditor, exercised only in a scratch repo, never in
this repo): a 5-commit source repo with a tag on commit 2, cloned with `--no-tags`,
then the same fetch run against it. `before: shallow=false tags=[]` /
`fetch rc=0` / `after: shallow=true tags=[v0.1.0]`, and `.git/shallow` was created.
Nothing is destroyed -- `git fetch --unshallow` or deleting `.git/shallow` restores
the clone -- which is why the ranking table's `fails-to-preserve` row (can ship
behind a trap.d fragment, does not block a release) applies rather than
`containment (write)` or `destroys`.

What would settle it: have the test fetch the missing tag into a throwaway
repository, or fetch it without `--depth` into a non-tag ref, instead of writing
into the developer's own `REPO_ROOT`.
