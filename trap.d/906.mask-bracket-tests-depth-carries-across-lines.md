Release audit for v0.43.1 (round 2, gate 3) flagged
.github/scripts/compile_hooks.py:517-583 (`_mask_bracket_tests`, added in c54e96b,
#906).

What was observed: an unbalanced `[` at a word boundary leaves the function's
tracked `depth > 0`, and that depth carries into every later physical line with
no reset. The dynamic-dispatch detector (`_DYNAMIC_CALL_RE`) therefore never sees
a genuine `"$fn"` call further down -- the mask treats it as still inside a
bracket-test span, the same shape #906 itself fixed in the other direction.

Effect: tree-shaking can then drop a function that is reachable only through that
dynamic call. A caller of the compiled hook would get "command not found", and
compiled hooks are what the release tree ships.

How it was confirmed: a script containing `fn="handler_$kind"` then `"$fn"`, with
a `tr -d [ < f` line two lines above the call (an unbalanced `[`). The new
compiler reports `dynamic=False shaken=True dropped=['handler_x']`; the v0.43.0
compiler on the same input reports `dynamic=True shaken=False dropped=[]`; the
same script without the stray `[` reports `dynamic=True` on the new compiler too.

Not triggered by any shipped hook today: the old and new compilers produce
byte-identical output for all four hooks.json hooks, and no dropped function is
still referenced in any compiled hook. CI's `hook-tests-compiled` job runs the
full suite against compiled hooks on 3 OSes, which would only catch this where a
test happens to exercise the dropped path.

What would settle it: whether bracket depth should carry onto the next physical
line only when that line ends in `&&`, `||`, `|` or a trailing backslash -- the
case the function's own docstring describes -- rather than carrying
unconditionally. Ranked `misreports` (the fix belongs in the detector's logic,
not the shaker) rather than `fails-to-preserve`; can ship behind a trap.d
fragment, does not block a release.
